# 工程项目生命周期与受约束动态表单引擎设计

- 状态：已确认增强设计方向
- 方案：C/A - 固定核心生命周期 + 强后台管理操作系统 + 受约束可视化工作流
- 初始日期：2026-07-10
- 更新日期：2026-07-11
- 文档版本：1.1
- 适用范围：招投标、项目管理、审计、资料、结算中心及后台设置

## 1. 背景与问题

当前系统已经具备项目、审计、资料、结算及部分字段配置能力，但业务规则仍主要分散在各页面和表单中。随着项目进入不同阶段，系统容易提前要求用户填写尚未产生的信息，或者允许用户选择与工程流程相悖的状态。

典型问题包括：

1. 项目尚未竣工或未验收合格，却出现送审、一审、二审等选项。
2. 项目处于合同签订阶段，却要求上传竣工验收证明或审计报告。
3. 同一字段在项目、审计、资料和结算模块重复录入，口径不一致。
4. 用户模型偏单角色，无法准确表达一人多岗、项目负责人和审核责任。
5. 字段配置主要解决显示、排序和必填，缺少条件规则、版本、权限和项目级覆盖。

## 2. 设计目标

系统以项目生命周期为主轴，以业务事件驱动表单、资料、待办和模块联动。

目标：

1. 固定工程项目主生命周期和核心阶段准入规则。
2. 支持一个用户拥有多个岗位角色，并在不同项目中承担不同项目角色。
3. 支持按企业、项目类型和单一项目配置阶段问卷。
4. 当前阶段只展示当前能够确认的信息，不把未来资料计为缺失。
5. 核心字段保持统一语义，供项目、审计、资料、结算和报表共同使用。
6. AI 只负责提取和建议，关键金额、条款和阶段变更必须经人工确认。
7. 建设独立的后台管理操作系统，使每个生命周期阶段的表单、资料、审批、条件和自动动作均可配置。
8. 提供可视化拖拽式工作流设计器，同时保护合同、验收、送审、审计、定案和归档等核心业务顺序。
9. 将合同、竣工验收证明、审计报告等文档识别真正接入业务表单和待办，而不是停留在文本摘要或演示界面。

## 3. 非目标

系统不建设完全自由且无保护的 BPM 平台。即使后台管理能力增强，也不允许管理员：

1. 任意删除系统核心生命周期阶段。
2. 通过配置绕过竣工验收、审计和归档的核心准入条件。
3. 编写 JavaScript、SQL 或任意执行脚本。
4. 将所有核心业务数据存入无类型 JSON 或纯 EAV 结构。
5. 让 AI 自动确认金额、自动推进项目阶段或覆盖人工确认数据。

管理员可以在核心阶段内部增加子流程、表单、判断、审批、资料、通知和自动任务，也可以配置核心阶段之间的进入条件；但不能删除核心阶段、颠倒受保护的业务顺序或解除法定和财务控制点。

## 4. 核心设计原则

1. **流程固定，问卷可配**：生命周期和核心门槛由系统保护，字段、布局和补充资料允许配置。
2. **事件驱动**：合同签订、验收合格、送审、一审完成等事件驱动后续任务和资料要求。
3. **一次录入，多处复用**：项目主数据、合同和金额字段由统一数据源提供。
4. **当前阶段最小必要信息**：没有走到的阶段不展示、不必填、不计缺失。
5. **配置有版本**：发布新模板不能静默改变历史记录。
6. **权限到动作和字段**：不仅控制菜单，还控制数据范围、操作、字段和文件。
7. **所有自动结果可解释**：金额计算、状态建议和 AI 识别均展示来源和过程。
8. **设计与运行分离**：管理员编辑的是草稿版本，生产项目只运行经过校验和发布的不可变版本。
9. **强后台、低前台负担**：复杂性集中在管理员终端，一线用户只看到与本人、当前项目和当前阶段有关的问题。
10. **核心保护、局部自由**：后台允许充分配置，但系统始终阻止不符合工程管理事实顺序的工作流。

## 5. 生命周期状态机

### 5.1 主生命周期

```text
机会发现
→ 投标登记
→ 待开标
→ 已中标
→ 已签订合同
→ 已进场施工
→ 施工中
→ 已竣工待验收
→ 验收合格
→ 资料准备中
→ 已送审
→ 一审中
→ 一审完成
→ 二审中 / 政府审计中
→ 二审完成
→ 最终定案
→ 收付款及质保期管理
→ 已结案归档
```

投标未中标、项目终止、验收不合格等情况作为分支结果，不直接删除历史项目。

### 5.2 生命周期规则矩阵

| 当前阶段 | 关键输入 | 阶段完成事件 | 下一阶段准入条件 | 自动动作 |
| --- | --- | --- | --- | --- |
| 投标登记 | 招标人、项目名称、开标时间、招标文件 | 投标登记完成 | 基础信息完整 | 生成待开标提醒和资料目录 |
| 已中标 | 中标金额、中标日期、中标通知书 | 中标确认 | 中标结果已确认 | 创建项目主档案，生成合同待办 |
| 已签订合同 | 合同主体、金额、日期、付款条款、合同附件 | 合同确认 | 合同金额大于 0，合同主体完整 | 提取付款条款，生成履约资料清单 |
| 已进场施工 | 进场日期、项目负责人、施工联系人 | 进场确认 | 已签订合同 | 生成施工阶段待办 |
| 施工中 | 进度、签证、付款申请、过程资料 | 竣工申报 | 工程已完成 | 生成验收准备清单 |
| 已竣工待验收 | 竣工日期、验收安排 | 验收结果确认 | 验收结果已填写 | 合格进入资料准备；不合格生成整改待办 |
| 验收合格 | 验收日期、验收证明 | 验收通过 | 验收结果为合格且证明齐全 | 开放送审问卷和结算资料清单 |
| 已送审 | 送审金额、送审日期、送审单位、资料 | 送审确认 | 已验收合格 | 同步审计看板，生成一审跟进待办 |
| 一审完成 | 一审单位、负责人、审定金额、报告 | 一审结果确认 | 一审报告或确认记录齐全 | 计算核减额和核减率，开放二审问卷 |
| 二审完成 | 二审单位、负责人、审定金额、报告 | 二审结果确认 | 二审资料完整 | 生成定案待办 |
| 最终定案 | 定案金额、日期、定案资料 | 定案确认 | 最终金额已确认 | 更新结算基数、发票和收付款待办 |
| 已结案归档 | 归档目录、质保金状态、结案确认 | 归档确认 | 必归档资料完整，高风险待办关闭 | 锁定核心数据，保留版本和操作日志 |

### 5.3 状态变更规则

1. 正向推进必须通过阶段准入校验。
2. 回退阶段必须填写原因，并记录回退前后状态、操作者和时间。
3. 禁止跨越核心阶段；确需补录历史项目时使用“历史项目初始化”，逐步确认已有事实。
4. 验收不合格时不得显示送审状态选择，系统只生成整改和复验任务。
5. 阶段完成后，核心事实字段默认锁定；有权限的用户通过更正流程修改。

### 5.4 核心流程保护与可配置边界

采用方案 A：核心生命周期受保护，阶段内工作流高度可配置。

| 配置对象 | 管理员能力 | 系统保护 |
| --- | --- | --- |
| 核心阶段 | 修改名称说明、配置进入条件、配置角色和表单 | 不可删除、不可改变受保护顺序 |
| 阶段内子流程 | 新增、删除、拖拽排序、建立分支和回路限制 | 必须有明确开始、结束和超时处理 |
| 条件判断 | 配置且、或、非及条件组 | 禁止脚本执行和无限循环 |
| 审批节点 | 配置审批人、会签、或签、驳回和转办 | 高风险节点不能无审批人直接通过 |
| 表单节点 | 选择表单模板、字段权限、必填和锁定 | 核心语义字段不能被删除或改型 |
| 资料节点 | 配置资料类型、份数、版本和必填条件 | 未来阶段资料不得提前计为缺失 |
| 自动动作 | 生成待办、提醒、目录、记录和计算结果 | 不能自动确认金额或自动完成高风险阶段 |
| AI 识别节点 | 选择识别模板、目标字段和置信度阈值 | 正式写入前必须经过人工确认 |

受保护的关键顺序至少包括：中标后才能确认合同、合同后才能进场、竣工后才能验收、验收合格后才能送审、审计结果确认后才能定案、归档前必须完成必归档资料检查。

## 6. 角色与权限模型

### 6.1 三层身份

| 层级 | 示例 | 用途 |
| --- | --- | --- |
| 岗位角色 | 招投标员、审计员、财务、行政、经理、资料员 | 决定模块和业务动作权限 |
| 项目角色 | 项目负责人、经办人、审核人、协作人 | 决定具体项目的数据范围和责任 |
| 系统角色 | 系统管理员 | 管理账号、模板、字典、权限和系统设置 |

行政岗位不自动获得系统管理权限；经理岗位不等同于项目负责人。

### 6.2 权限计算

```text
最终权限 = 多岗位角色权限并集
         ∩ 数据范围
         ∩ 当前项目角色权限
         ∩ 当前生命周期阶段允许动作
         - 显式禁止权限
```

显式禁止优先于允许。用户不需要频繁切换角色，系统在“我的工作”中合并其所有授权任务，并显示当前操作所依据的角色。

### 6.3 角色权限矩阵

| 角色 | 默认数据范围 | 主要职责 | 受限动作 |
| --- | --- | --- | --- |
| 招投标员 | 本人及被授权投标项目 | 机会、投标、开标、中标移交 | 不确认审计金额和收付款 |
| 项目负责人 | 负责或参与项目 | 合同确认、进场、施工、验收准备 | 不确认财务到账和最终审定金额 |
| 审计员 | 被分配审计项目 | 送审、一审、二审、定案资料和进度 | 不修改原始合同金额 |
| 财务 | 被授权结算项目 | 发票、应收、实收、付款、质保金 | 不独立改变工程验收结果 |
| 资料员 | 被授权项目 | 资料收集、分类、版本和归档 | 不确认业务金额和阶段结论 |
| 行政 | 被授权行政范围 | 通讯录、基础组织信息、行政协作 | 默认无系统配置权限 |
| 经理 | 授权范围或全公司 | 查看、督办、复核、高风险确认 | 不直接替代经办事实录入 |
| 系统管理员 | 全系统 | 账号、角色、模板、字典和系统设置 | 不因系统权限自动获得业务确认权 |

小型公司允许同一人兼任经办和复核，但系统必须提示职责重叠，并保留完整日志。金额确认、付款确认、阶段回退和归档可配置为必须二次确认。

## 7. 动态表单引擎

### 7.1 模板继承

```text
系统核心模板
  → 企业生命周期模板
    → 项目类型模板
      → 单一项目覆盖
```

运行时优先级：单项目覆盖 > 项目类型模板 > 企业模板 > 系统核心模板。

系统核心模板保存生命周期所需的语义字段和准入规则。企业和项目只能在允许范围内覆盖标签、说明、排序、布局、补充字段、角色权限及更严格的资料要求。

### 7.2 字段定义

每个字段至少包含：

| 属性 | 说明 |
| --- | --- |
| semanticKey | 稳定语义标识，发布后不可随意修改 |
| label | 用户可见名称 |
| type | 文本、金额、日期、人员、单位、单选、多选、文件等 |
| stageKey | 所属生命周期阶段 |
| dataSource | 手填、项目带出、合同带出、系统计算、AI 建议 |
| requiredRule | 必填条件 |
| visibleRule | 显示条件 |
| editableRule | 可编辑条件 |
| allowedRoles | 可见和可编辑角色 |
| validation | 格式、范围、交叉字段校验 |
| optionGroup | 业务字典来源 |
| formula | 受支持的安全计算公式 |
| evidenceType | 需要关联的资料类型 |
| aiMapping | AI 提取目标及置信度阈值 |
| reporting | 是否用于查询、统计和导出 |
| sensitivity | 普通、敏感、脱敏展示 |

### 7.3 支持的规则

第一阶段只支持可视化、安全且可解释的规则：

1. 显示或隐藏字段、分组和后续问题。
2. 设置必填、只读、默认值和自动带出。
3. 执行白名单公式，如金额加减乘除、比例和日期间隔。
4. 要求上传指定资料。
5. 阶段准入校验。
6. 生成待办、提醒或复核任务。
7. 根据答案建议下一阶段，但不绕过确认。

规则示例：

```text
当“验收结果 = 合格”时：
- 显示“验收日期”和“验收证明”；
- “验收证明”设为必填；
- 允许进入“资料准备中”；
- 开放送审问卷。

当“验收结果 = 不合格”时：
- 隐藏全部送审字段；
- 禁止进入送审阶段；
- 生成整改和复验待办。
```

### 7.4 系统保护字段

以下核心字段不得删除、改变语义类型或取消核心校验：

1. 项目唯一标识和项目编号。
2. 建设单位、施工单位和合同主体。
3. 合同金额、合同日期和合同唯一标识。
4. 竣工验收结果、验收日期。
5. 送审、一审、二审、定案金额和日期。
6. 发票、收付款、质保金记录。
7. 当前生命周期阶段及阶段历史。

管理员可以调整这些字段的标签、帮助说明和布局，也可以提高必填要求，但不能降低系统核心门槛。

### 7.5 单项目覆盖

单项目配置支持：

1. 增加项目特有字段和资料类型。
2. 调整字段顺序、分组、说明和可见角色。
3. 将企业模板中的可选字段提升为必填。
4. 停用非核心的扩展字段。

单项目配置不得影响其他项目，不得取消核心字段、核心准入规则或已经发生的历史事实。

### 7.6 可视化工作流设计器

后台提供节点连线式工作流画布。管理员从左侧节点库拖入节点，在画布中连接业务路径，在右侧属性面板配置规则。

支持的节点类型：

1. 开始、结束和阶段进入节点。
2. 表单问卷节点。
3. 条件判断和多分支路由节点。
4. 单人审批、或签、会签和经理复核节点。
5. 资料上传与资料完整性检查节点。
6. AI 文档识别和人工确认节点。
7. 金额公式与日期计算节点。
8. 创建待办、通知、提醒和超时升级节点。
9. 写入业务记录和同步其他模块节点。
10. 子流程调用节点。

画布必须提供缩放、自动排版、小地图、撤销重做、复制节点、批量对齐、节点搜索、错误定位和只读版本对比。管理员不能直接在生产版本上编辑，必须先创建草稿。

### 7.7 条件规则编辑器

条件配置采用结构化规则，不允许编写 JavaScript 或 SQL。规则支持：

```text
当 [验收结果] [等于] [合格]
并且 [验收证明] [已上传]
则 [允许进入资料准备中]
否则 [生成整改与复验待办]
```

条件来源包括表单字段、项目主数据、角色、资料状态、日期、金额、流程执行结果和 AI 人工确认结果。支持条件组、且或关系、空值判断、包含判断、金额比较、日期间隔和字典值判断。

系统在保存和发布前检查：

1. 不可达节点和无出口节点。
2. 循环路径和缺少终止条件的回路。
3. 相互矛盾或永远成立的条件。
4. 被引用但已停用的字段、角色或字典项。
5. 无操作权限的审批人和权限死锁。
6. 违反核心生命周期保护规则的连线。

### 7.8 工作流运行机制

每个项目在进入阶段时创建工作流实例，并绑定工作流发布版本。运行中的实例不随后台草稿变化。

节点执行状态统一为：未到达、待处理、处理中、已完成、已驳回、已跳过、已超时、执行失败、已取消。每次执行保存输入、输出、操作者、开始结束时间、规则命中过程和错误信息。

自动节点必须具备幂等键和重试策略，避免重复创建待办、资料目录或财务记录。人工任务被撤回或阶段回退时，系统按补偿规则关闭后续未完成任务，但保留历史。

### 7.9 表单组件能力

除文本、数字、日期和选择项外，后台表单设计器还应支持：

- 金额输入并同步显示元、万元和中文大写；
- 单位、人员、项目、合同和资料引用；
- 文件上传、附件版本和资料分类；
- 表格子项、重复分组和付款节点明细；
- 地址、联系电话、百分比、税率和计算结果；
- 电子签名状态、确认声明和风险提示；
- AI 建议值、原文证据和人工确认状态；
- 只读业务摘要和跨模块引用信息。

字段支持按角色设置隐藏、只读、可编辑和脱敏。管理员预览时可以切换角色、项目类型、阶段和测试数据，看到一线用户的真实填写效果。

## 8. 模板版本与历史数据

模板状态为：草稿、已发布、已停用。

1. 每次发布生成不可变版本号。
2. 表单实例记录模板 ID、版本号和填写快照。
3. 新版本默认只应用于新进入该阶段的项目。
4. 在办项目迁移前必须展示影响范围、字段变化和缺失数据。
5. 删除扩展字段采用停用方式，历史值继续可查。
6. 迁移失败不得产生半完成状态，保留原版本并记录失败原因。
7. 所有发布、迁移和项目覆盖操作进入审计日志。

## 9. 后台管理操作系统

后台管理不再只是若干配置表格，而是面向系统管理员、业务管理员和审计管理员的独立操作终端。

### 9.1 信息架构

| 一级模块 | 核心能力 |
| --- | --- |
| 管理驾驶舱 | 配置健康度、待发布草稿、失败任务、AI 队列、数据异常和近期变更 |
| 组织与用户 | 用户、部门、岗位角色、项目角色、数据范围和账号状态 |
| 权限中心 | 模块、动作、字段、资料、项目范围和高风险二次确认策略 |
| 生命周期中心 | 核心阶段、阶段说明、进入退出条件、阶段负责人和保护规则 |
| 表单中心 | 表单设计器、组件库、字段语义库、模板继承和项目覆盖 |
| 工作流中心 | 可视化流程画布、规则、审批、自动动作、子流程和运行监控 |
| 资料规则中心 | 资料分类、阶段目录、必填条件、版本、归档和预览策略 |
| 业务字典 | 单位、人员、状态、项目类型、资料类型和可新增选项审核 |

| 发布与版本 | 草稿包、差异对比、模拟测试、审批发布、回滚和迁移任务 |
| 日志与诊断 | 配置日志、运行日志、错误追踪、接口调用和数据修复入口 |
| 系统设置 | 上传限制、编号规则、金额精度、通知策略和安全设置 |

### 9.2 三类可视化设计器

1. **生命周期设计器**：以受保护阶段轨道展示全局流程，允许配置阶段属性和阶段内子流程，不允许破坏核心顺序。
2. **表单设计器**：左侧组件库、中间表单画布、右侧属性和规则面板，支持拖拽分组、字段和资料组件。
3. **工作流设计器**：左侧节点库、中间连线画布、右侧节点条件属性，下方显示校验错误和测试轨迹。

三类设计器共享字段语义库、角色库、资料类型、业务字典和规则表达式，避免同一概念在不同后台页面重复定义。

### 9.3 配置作用范围

管理员创建配置时必须先选择作用范围：

```text
系统默认 → 企业全局 → 项目类型 → 指定项目
```

页面持续显示当前作用范围，防止管理员误把单项目配置发布到全公司。指定项目配置必须展示与上级模板的差异，并可一键恢复继承。

### 9.4 管理员角色分级

- 系统管理员：管理平台、账号、集成、发布和安全策略。
- 业务管理员：配置被授权模块的表单、流程、字典和资料规则。
- 审计管理员：查看全部配置变更、版本和运行日志，但不能直接修改生产配置。
- 项目配置员：只能为被授权项目增加扩展字段或提高资料要求。

### 9.5 沙箱模拟与发布

每次发布必须经过：保存草稿、自动校验、沙箱模拟、影响分析、发布审批和正式生效。

沙箱允许管理员选择项目类型、生命周期阶段、用户角色和测试答案，逐步运行流程，观察显示字段、条件命中、审批人、自动待办和资料要求。系统提供内置正向和反向测试案例，例如“未验收不能送审”“金额超过合同金额必须拦截”。

影响分析至少展示：受影响模板、项目数量、在办实例、字段变化、权限变化、待迁移数据和无法自动迁移的项目。高风险发布必须由另一名管理员或经理复核。

### 9.6 运行监控

后台应提供工作流实例监控图，显示项目当前节点、等待人员、停留时长、失败自动动作和超时情况。管理员可以重试失败的自动节点、转交人工任务或发起受控回退，但不能直接篡改已确认业务结果。

## 11. AI 文档识别落地设计

AI 识别是正式业务能力，不是聊天摘要或一次性 OCR。优先落地合同和竣工验收证明，再扩展审计、发票和付款资料。

### 11.1 识别范围

| 文档类型 | 重点提取字段 |
| --- | --- |
| 施工合同 | 合同名称编号、主体、金额、日期、工期、税率、付款条款、质保金、违约条款 |
| 中标通知书 | 项目名称、中标单位、中标金额、日期、工期和招标人 |
| 竣工验收证明 | 项目名称、参建单位、竣工日期、验收日期、验收结论、签章页 |
| 竣工结算书 | 送审金额、编制单位、日期和项目范围 |
| 一审二审报告 | 送审金额、审定金额、核减金额、核减率、审计单位、人员和日期 |
| 定案资料 | 最终审定金额、定案日期、确认单位和签章情况 |
| 发票 | 发票号码、日期、购销双方、税率、金额、税额和价税合计 |
| 收付款凭证 | 付款方、收款方、金额、日期、用途和流水号 |

### 11.2 识别处理流程

```text
上传文件
→ 文件分类和安全检查
→ OCR / PDF 文本提取
→ 条款和字段识别
→ 展示页码、原文、置信度和建议值
→ 用户逐项确认或修正
→ 写入合同和付款条款
→ 规则引擎生成付款节点和待办
```

上传后先进行文件类型、大小、恶意文件和重复文件检查。可复制文本 PDF 优先使用本地解析；扫描 PDF 和图片进入 OCR 与版面解析。大模型只接收必要文本片段和字段要求，输出符合 JSON Schema 的候选值。

### 11.3 人工复核界面

复核界面采用左右对照：左侧原文件及定位页，右侧候选字段、原文证据、置信度和业务校验结果。用户可接受、修改或拒绝单个字段，也可查看付款条款拆分过程。

金额、日期、单位和人员必须执行交叉校验，例如合同总额与大小写金额是否一致、付款比例合计是否合理、验收证明项目名称是否匹配当前项目。低置信度、冲突值和缺少证据的字段必须高亮，不允许批量静默写入。

### 11.4 识别模板后台

管理员可以按文档类型配置：目标字段、字段说明、示例、是否必提取、允许格式、字典映射、校验规则、置信度阈值、复核角色和写入目标。识别模板同样采用版本发布机制。

### 11.5 API 与供应商适配

AI 落地需要两类外部能力，系统必须通过适配器接口接入，不能把供应商协议写死在业务代码中：

1. **OCR 与版面解析 API**：处理扫描 PDF、表格、印章页和复杂版式，返回文字、坐标、页码和表格结构。
2. **支持结构化输出的大模型 API**：按指定 JSON Schema 提取合同条款和业务字段，并返回证据引用。

文件存储、病毒扫描和消息通知可继续使用现有能力；若现有能力不足，再作为独立集成补充。API 密钥只保存在服务端加密配置或环境变量中，绝不进入浏览器、代码仓库、操作日志或 Obsidian 记忆库。

### 11.6 识别效果指标

后台按文档类型统计任务量、成功率、平均耗时、字段接受率、字段修改率、低置信度率和人工复核时长。指标只使用真实识别任务，不生成演示数据。

AI 不得：

1. 静默覆盖人工确认数据。
2. 自动确认合同金额、审定金额或付款金额。
3. 自动推进生命周期阶段。
4. 无来源页和原文时写入正式数据。

AI 识别失败时保留原文件和任务记录，允许重试、切换供应商或完全人工录入，不能阻塞其他不依赖识别结果的业务操作。

后续按实际需求扩展中标通知书、验收资料、审计报告、发票和付款凭证识别。

## 12. 异常处理与可追溯性

1. 所有规则校验返回用户可理解的业务原因和解决入口。
2. 配置错误在发布阶段阻断，不把错误留给一线用户。
3. 阶段推进采用事务处理：阶段事件、表单锁定、待办和资料清单必须同时成功或全部回滚。
4. 操作日志保存人员姓名、账号、角色、项目、动作、前后值、时间和来源。
5. AI、公式和自动规则均保存输入、输出、版本和人工确认结果。
6. 集成密钥必须加密存储并只允许系统管理员更新，后台只能显示脱敏状态。
7. 工作流发布、回滚、实例人工干预和 AI 人工复核均写入不可篡改审计日志。
8. 自动任务使用重试、退避、死信队列和人工处置入口，避免失败任务无限循环。
9. 文件识别应设置租户、用户和文件级权限，临时解析文件按保留策略清理。
10. 删除模板、字段和工作流采用停用或归档，不直接物理删除仍被历史实例引用的配置。

## 13. 分期实施

### 第一阶段：后台规则底座（P0）

1. 确定生产唯一事实源、核心领域模型、稳定业务 ID 和历史数据迁移方案。
2. 建立项目、合同、标段、阶段事件、资料版本和金额记录的关系模型。
3. 建立多角色 RBAC、项目成员、数据范围、字段权限和高风险职责分离。
4. 建立语义字段库、动态表单元数据、配置合并协议和核心字段保护。
5. 实现生命周期状态机、异常路径、阶段准入、回退、更正和操作日志。
6. 实现工作流声明模型、运行快照、幂等执行、并发控制、节点日志和失败恢复。
7. 建立草稿、自动校验、发布、不可变版本、影响分析、回滚和迁移框架。
8. 完成旧角色、历史项目和现有关键字段的试迁移与对账，不直接切换生产。

### 第二阶段：强后台与 AI 首批落地（P1）

1. 建设基础模式表单向导、表单设计器和企业、项目类型、单项目模板继承。
2. 建设当前阶段资料清单、正式资料证据链、通知协议和统一“我的工作”。
3. 将项目、审计和结算的现有关键表单按业务阶段逐批迁入引擎。
4. 完成沙箱模拟、配置依赖图、发布差异和在办项目受控迁移。
5. 在运行内核稳定后建设专家模式工作流画布、条件编辑器和实例监控。
6. 建立 AI 适配器、识别模板、金标准评估、成本配额和人工复核工作台。
7. 落地合同与竣工验收证明识别、证据定位和人工确认写入。
8. 建设 OCR、大模型、对象存储、病毒扫描和通知集成配置中心。
9. 完成生产数据库切换、对账、恢复演练和观察期，确认后关闭旧写入路径。

### 第三阶段：扩展识别与运营治理（P2）

1. 一审、二审、定案、发票和付款凭证识别。
2. 自动生成付款节点、资料清单和待办并展示计算过程。
3. 完善多合同、分段验收、退审补件、质保金分批释放等复杂业务模板。
4. 配置健康度、识别质量、任务积压和工作流效率分析。
5. 在真实数据量、数据质量和业务样本量达标后建设预测与分析。

## 14. 验收标准

1. 合同签订阶段不展示验收、送审和审计字段。
2. 未竣工、未验收或验收不合格时，送审问卷不可见且接口拒绝推进。
3. 多角色用户在统一任务中心看到合并后的授权任务，不重复生成。
4. 用户只能查看授权范围内的项目和字段。
5. 单项目扩展字段不影响其他项目。
6. 模板新版本不改变历史表单实例和历史导出结果。
7. 模板发布前能够发现核心字段缺失、循环规则和权限死锁。
8. AI 提取结果必须展示来源页、原文和置信度，并经人工确认。
9. 阶段回退、金额更正和归档均有完整操作日志。
10. 当前阶段未产生的未来资料不计入资料缺失率。
11. 每个核心生命周期阶段均可绑定独立表单和阶段内工作流。
12. 管理员可以拖拽创建条件、审批、资料、AI、通知和自动动作节点。
13. 系统能够阻止删除核心阶段、颠倒受保护顺序和发布无效流程。
14. 工作流草稿不会影响正在运行的项目，新版本发布后历史实例仍可追溯。
15. 指定项目表单和流程覆盖不会影响其他项目，并可查看继承差异。
16. 沙箱能够模拟不同角色、项目类型和答案路径，并显示命中规则和生成任务。
17. 合同和验收证明识别结果能够定位到原文页和区域，逐字段人工确认后写入。
18. OCR 或大模型服务不可用时能够重试、切换供应商或回退人工录入。
19. API 密钥不出现在前端、仓库、日志、导出文件和记忆库中。
20. 后台能够查看失败节点、超时实例、待复核 AI 任务和配置发布历史。
21. 多合同、补充协议、停工复工、整改复验和退审补件均保留事件和版本，不覆盖历史事实。
22. 同一阶段实例在配置发布后继续使用原运行快照，迁移前可查看差异并回滚。
23. 并发提交、重复消息和自动节点重试不会重复推进阶段或创建重复业务记录。
24. 列表、详情、搜索、统计、导出和附件下载使用同一数据范围与字段权限。
25. 历史迁移能够按项目核对数量、金额、附件和阶段，并输出无法自动确认的清单。
26. 正式资料原件、版本、派生文件和 AI 结果具备完整哈希及证据关联。
27. AI 新版本必须通过独立金标准回归，高风险字段未达阈值时不得发布。
28. 生产发布前完成备份恢复、供应商不可用、队列积压和通知失败演练。
29. 后台基础模式可以完成常见阶段表单和资料规则配置，无需使用复杂工作流画布。
30. 配置冲突、权限死锁、无默认出口、不可达节点和引用停用对象均在发布前阻断。

## 15. 已确认决策

1. 采用固定生命周期和受约束动态表单引擎，不建设完全自由 BPM。
2. 一个用户可拥有多个岗位角色，并可在不同项目承担不同项目角色。
3. 系统管理员与行政岗位分离，项目负责人作为项目角色管理。
4. 支持企业、项目类型和单项目三级业务配置，系统核心模板作为不可绕过的底座。
5. 核心业务数据使用关系模型，扩展字段使用类型化动态值。
6. 模板采用发布和版本机制，历史实例不可被新配置静默修改。
7. AI 只提供建议，关键业务事实必须人工确认。
8. 采用方案 A：核心生命周期受保护，阶段内表单、条件、审批、资料、AI 和自动动作高度可配置。
9. 后台管理升级为独立操作系统，包含设计、模拟、发布、运行监控、集成和诊断能力。
10. 合同与竣工验收证明作为第一批正式落地的 AI 文档识别类型。

## 16. AI 实施前需要的外部输入

进入 AI 开发前，需要用户或企业提供以下资源，不应在设计阶段写入真实密钥：

1. OCR 与版面解析服务的供应商、接口地址、区域和测试凭据，或者确认采用本地 OCR 作为第一版。
2. 支持结构化 JSON 输出的大模型服务、模型名称、接口地址和测试凭据。
3. 已脱敏的真实合同、竣工验收证明、审计报告样本，用于定义字段和验收准确率。
4. 文件是否允许发送到第三方服务、允许发送的文档类型及数据保留要求。
5. 合同和验收证明每个目标字段的业务解释、必填规则和人工复核责任角色。

建议第一批至少准备 20 份版式有差异的脱敏合同和 20 份脱敏竣工验收证明。样本仅用于建立和验证识别模板，不进入演示数据或公开测试集。

## 17. 工程异常、并行流程与业务对象边界

### 17.1 状态、事件和任务必须分离

系统不得把所有业务动作都设计成项目状态。三类概念定义如下：

| 概念 | 定义 | 示例 |
| --- | --- | --- |
| 生命周期阶段 | 项目在较长时间内所处的受保护业务位置 | 已签订合同、施工中、已送审、一审中 |
| 阶段事件 | 已经发生且需要永久留痕的业务事实 | 合同补充协议签订、停工、复工、整改完成、退审 |
| 工作任务 | 为完成阶段目标而分配的可关闭事项 | 上传验收证明、补充一审资料、确认付款节点 |

同一项目在任一时刻只能有一个主生命周期阶段，但可以同时存在多个阶段事件、子流程和任务。阶段事件不能通过删除任务而消失。

### 17.2 必须支持的工程异常路径

1. 投标未中标、废标、流标和主动放弃，保留投标资料和结果，不生成正式施工项目。
2. 合同签订前项目取消；合同签订后解除、终止或暂停履约，必须记录原因、日期、责任方和关联资料。
3. 施工阶段支持停工、复工、延期、现场签证、设计变更、索赔和补充协议，不因这些事件改变主阶段语义。
4. 支持分段、分楼栋、分标段竣工和验收；项目主阶段是否进入“验收合格”由配置的汇总规则判断。
5. 验收不合格进入“整改与复验”受控回路，复验通过前不得送审。
6. 送审后支持退审补件、重新送审、审计争议复核和多轮意见回复，保留每轮送审批次。
7. 一审完成后允许按企业规则进入二审、政府审计或直接定案，但不得跳过人工确认和相应资料校验。
8. 定案后允许更正，但必须通过高风险更正流程，不得覆盖原定案事实。
9. 支持质保期延长、分批释放质保金和质保责任未关闭，质保事项未完成时不得将项目标记为完全结案。

### 17.3 多合同、标段和子项目

项目、合同、标段、楼栋和结算对象不得混为同一个实体：

```text
项目主档案
  → 一个或多个标段 / 子项目
    → 一个或多个合同及补充协议
      → 一个或多个付款条款和结算对象
```

合同金额变化必须通过补充协议、签证或正式更正记录形成版本，不允许直接覆盖原合同金额。审计和结算记录必须明确关联项目、合同及适用标段；跨合同汇总只作为展示结果，不作为原始业务记录。

## 18. 配置解析协议与运行快照

### 18.1 配置合并规则

四级配置解析仍遵循“单项目覆盖 > 项目类型 > 企业全局 > 系统核心”，但不同属性采用不同合并策略：

| 配置属性 | 合并策略 |
| --- | --- |
| 标签、说明、布局、排序 | 下级可以覆盖 |
| 补充字段、资料类型、通知 | 下级追加，可停用自身新增项 |
| 必填、准入、审批和资料要求 | 下级只能保持或提高要求，不能降低系统保护门槛 |
| 字段可见和编辑权限 | 先满足数据范围，再取所有命中规则中的最严格权限 |
| 公式、写入目标、语义类型 | 发布后不可由下级改写，只能创建新语义字段 |
| 核心阶段顺序和高风险确认 | 不允许覆盖 |

如果同一优先级出现互斥规则，发布校验必须阻断并展示冲突来源，不允许依赖规则保存顺序决定结果。

### 18.2 运行配置快照

每个阶段实例创建时生成不可变运行快照，至少包含：

- 生命周期版本、工作流版本和表单版本；
- 字段定义、规则、字典版本和资料要求；
- 角色与字段权限决策版本；
- 公式版本、通知策略和集成适配器版本；
- 配置作用范围、解析结果哈希和生成时间。

运行实例只读取快照，不在执行过程中重新合并后台配置。配置发布后通过事件使缓存失效；在办实例是否迁移必须形成独立迁移任务、差异报告和回滚点。

### 18.3 配置依赖和生命周期

字段、字典、公式、工作流、资料规则和报表之间建立引用图。停用任何对象前必须检查依赖，仍被发布版本或历史实例引用时只能归档，不能物理删除。配置包支持导出、导入、校验和环境间发布，但不得包含密钥、真实项目数据或用户隐私信息。

## 19. 工作流执行协议

### 19.1 节点执行和并发控制

1. 每个工作流实例、节点执行和人工任务均带版本号，更新时使用乐观锁，冲突时提示用户刷新，不得以后提交覆盖先提交。
2. 自动节点必须使用由“实例 ID + 节点 ID + 业务动作”生成的幂等键；重试不得重复生成待办、资料目录、发票或财务记录。
3. 业务写入与事件发布使用事务事件表。消费者使用 Inbox 去重，按项目和流程实例保证同一业务键的事件顺序。
4. 人工任务只允许一次有效完成；重复点击、网络重试和多端同时提交返回同一业务结果。
5. 阶段推进必须在数据库事务内校验当前阶段和实例版本，确保一个项目不会同时进入两个主阶段。

### 19.2 分支、汇合和审批

- 条件分支必须有明确默认出口；多个条件同时命中时按显式优先级执行，不以画布位置决定。
- 并行分支必须配置汇合策略：全部完成、任一完成、达到指定数量或表达式满足。
- 会签必须配置通过比例、拒绝策略、人员变更策略和超时策略；审批发起后新增角色成员默认不自动加入当前任务。
- 或签由首个有效结论结束其余任务，其余任务标记为已取消并保留记录。
- 子流程必须定义输入、输出、超时、取消和失败传播规则，不能直接共享可变内部状态。

### 19.3 时间、超时和通知

企业可配置工作日历、节假日、工作时间和时区。所有到期规则明确使用自然日、工作日或固定日期。修改日历不得静默改变已经生成的到期日；如需重算，必须形成可审计批处理任务。

通知与业务任务分离。通知失败不能回滚已经成功的业务事实，但进入重试和人工处置队列。阶段回退、任务取消或责任人变化时，系统撤销尚未发送的失效通知并对已发送通知生成更正消息。

### 19.4 回退、撤回和补偿

每个可回退节点必须声明补偿动作和不可逆边界。以下行为不得自动补偿：已确认金额、已开具发票、已发生收付款、已归档原件和已外发正式通知。涉及这些事实时只能创建更正记录、冲销记录或人工处理任务。

管理员人工干预只允许重试、转交、取消未完成任务、执行受控回退或恢复失败实例，不允许直接把节点改为已完成。所有干预保存原因、审批人、前后状态和关联工单。

## 20. 权限执行模型与职责分离

### 20.1 授权决策顺序

后端对每次请求统一执行以下判断，前端隐藏按钮不能代替后端授权：

```text
账号状态
→ 模块与动作权限
→ 企业 / 部门 / 项目数据范围
→ 项目成员和项目角色
→ 生命周期阶段权限
→ 字段、资料和金额敏感权限
→ 高风险二次确认或双人复核
```

任何一层拒绝即拒绝请求，并返回可理解但不泄露敏感信息的原因。权限决策结果保存策略版本和命中规则，便于审计追溯。

### 20.2 多角色和项目角色

招投标员、审计员、财务、行政、经理和资料员属于岗位角色，一个用户可以拥有多个岗位角色。项目负责人、合同经办人、一审负责人、二审负责人、资料责任人等属于项目角色，必须通过项目成员关系授权，不得写死为全局角色。

同一用户命中多个角色时：可见范围取授权范围并集，字段编辑和敏感数据权限取命中规则中最严格限制，高风险职责分离规则优先于角色并集。

### 20.3 数据范围和字段权限

数据范围至少支持本人、本人参与项目、部门、指定项目、指定项目类型和企业全局。字段权限分为隐藏、脱敏、只读、可编辑；资料权限分为不可见、只看元数据、预览、下载、上传、替换和归档。

列表查询、统计、导出、搜索联想和附件下载必须使用同一数据范围策略，防止用户通过导出或搜索结果绕过页面权限。

### 20.4 高风险职责分离

以下动作默认不能由同一人独立发起并最终批准：

1. 生产配置高风险发布与审批。
2. 合同金额、审定金额、付款基数和收付款记录更正。
3. 生命周期跨阶段回退和项目结案归档。
4. 权限提升、密钥更新和审计日志导出。

小型企业确需同人处理时，系统管理员可以配置例外，但必须二次确认、填写原因并通知经理，例外本身进入审计日志。

### 20.5 现有角色迁移

现有 admin、editor、viewer 不直接作为长期业务角色使用。迁移时建立旧角色到新权限包的显式映射，先生成权限差异报告，再由系统管理员确认。迁移期间所有新接口按新授权服务判断，旧接口仅作为受控兼容层，禁止长期维持两套互相独立的权限规则。

## 21. 数据迁移、唯一事实源与报表语义

### 21.1 唯一事实源

正式开发前必须在架构决策记录中确定生产关系数据库、文件存储和身份服务的唯一事实源。SQLite、Supabase 或其他现有存储只能按迁移计划承担明确角色，不允许同一合同、金额、阶段或权限数据由两个系统分别作为主记录。

模块之间通过稳定业务 ID 和服务接口引用同一项目、合同、单位、人员和资料记录，不复制形成独立主数据。看板、列表和统计均由真实业务记录计算，无数据时展示空状态，不生成模拟数据。

### 21.2 历史数据迁移流程

历史迁移按以下顺序执行：

```text
数据盘点与备份
→ 字段和字典映射
→ 数据清洗与冲突清单
→ 只读试迁移
→ 数量、金额、附件和权限对账
→ 业务人员抽样确认
→ 增量同步
→ 受控切换
→ 观察期与可回滚备份
```

每条历史项目记录保存来源系统、来源主键、迁移批次和转换规则。无法确定的事实不得猜测，统一进入“待确认”状态和人工处理清单。历史项目通过专用初始化向导逐阶段确认已有事实，不伪造阶段完成时间。

### 21.3 语义字段库

报表、搜索、导出和接口使用 `semanticKey`，不使用可变的中文标签作为字段标识。语义字段库必须定义：数据类型、单位、精度、币种、空值含义、聚合方式、敏感等级、来源实体和版本兼容规则。

动态扩展值按类型保存并建立受控索引。只有标记为可报告且通过发布校验的字段才能用于筛选、排序和聚合。跨模板统计时，仅合并相同语义和兼容类型的字段；无法兼容的字段分别展示，不进行隐式换算。

### 21.4 金额和快照

金额统一保存为最小货币单位或固定精度十进制数，禁止使用浮点数。每条金额记录保存币种、原始单位、录入值、计算公式版本和业务基准。合同、审计、结算、发票及收付款的正式导出使用生成时快照，后续更正不能静默改变历史导出结果。

## 22. 正式资料证据链

### 22.1 原件、版本和派生文件

1. 原始上传文件写入不可变对象存储并计算 SHA-256，业务系统保存文件 ID、哈希、大小、MIME 类型、上传人、上传时间和来源。
2. 替换文件生成新版本，不覆盖旧版本；版本关系和当前有效版本由业务记录管理。
3. 预览图、转码 PDF、缩略图、OCR 文本和 AI 结构化结果均为派生文件，不得替代原件。
4. 下载、预览、上传新版本、归档、恢复和删除申请均进入资料审计日志。
5. 重复文件根据哈希提示用户，但是否复用必须结合项目、资料类型和访问权限判断。

### 22.2 AI 证据定位

每个 AI 候选值必须绑定原始文件版本、页码、坐标区域、原文片段、解析器版本和模型版本。用户确认后保存候选值、确认值和修改差异。原文件版本变化时，旧识别结果自动标记为基于历史版本，不得继续作为当前资料的未提示建议。

印章、签字和手写内容只允许标记“检测到疑似区域”和识别置信度，不得自动判断法律真实性、授权有效性或合同已正式生效。

### 22.3 保留与清理

管理员可按资料类型配置保留期限、归档策略和临时解析文件清理期限，但受法律、合同和审计要求保护的原件不得由普通管理员物理删除。删除采用申请、审批和延迟执行机制，并保留删除凭证；备份中的数据按备份生命周期到期清理。

## 23. AI 生产验收与供应商治理

### 23.1 数据边界优先

选择 OCR 或大模型供应商前，企业必须确认每类资料是否允许出域、允许发送的内容范围、供应商保留策略、服务区域和数据删除要求。禁止将完整资料发送给仅需要局部文本即可完成任务的模型。

集成层统一提供 OCR、版面解析和结构化提取接口。业务代码只依赖内部协议；供应商切换不得改变合同、验收和审计实体的业务结构。

### 23.2 金标准评估集

首批样本用于字段设计和提示词调试，生产验收必须另建互不重叠的金标准测试集。测试集按扫描件、可复制 PDF、复杂表格、印章页、低清晰度和不同合同版式分层，并由业务人员标注正确字段和证据页。

每个文档类型分别统计：

- 文档分类准确率；
- 字段精确率、召回率和完全正确率；
- 金额、日期、主体和比例等关键字段的独立准确率；
- 证据页与坐标定位准确率；
- JSON Schema 合规率、任务成功率和平均处理时间；
- 人工接受率、修改率、拒绝率和平均复核时间。

### 23.3 上线门槛

合同金额、合同主体、合同日期、付款比例、验收结论、审定金额等高风险字段必须达到企业批准的独立验收阈值，并始终人工确认。未达到阈值的字段可以作为低置信度提示，不得进入批量确认入口。

模型、OCR、提示词、识别模板或后处理规则变更时必须重新执行固定回归集。评估结果与版本绑定，未通过回归的版本不得发布到生产。

### 23.4 成本、降级和反馈闭环

后台按供应商和文档类型配置单文件页数、大小、并发、超时、重试和成本上限。超出限制时提示具体原因，并允许拆分文件或转人工录入。供应商不可用时按批准顺序降级，禁止在未告知用户的情况下切换到不满足数据边界的供应商。

用户修正结果只进入质量分析和候选规则优化队列，不直接自动训练或修改生产提示词。任何优化都经过脱敏、版本、回归和发布审批。

## 24. 后台可用性与配置治理

### 24.1 基础模式和专家模式

后台默认进入基础模式，通过工程业务语言配置阶段表单、负责人、资料清单和提醒。专家模式才开放复杂条件、并行分支、子流程、公式和集成节点。两种模式生成相同的声明式配置，基础模式不是另一套运行引擎。

### 24.2 内置模板和安全默认值

系统提供经验证的施工项目、审计项目和结算项目模板。创建配置时优先复制模板，不从空白画布开始。默认策略包括：未来阶段字段隐藏、高风险金额人工确认、验收不合格禁止送审、正式发布需要影响分析、资料缺失生成待办而非伪造完成。

### 24.3 防误操作

1. 编辑生产配置前自动创建草稿和编辑锁，避免多人同时覆盖。
2. 发布差异同时提供技术视图和业务语言摘要，例如“新增 2 个必填资料，将影响 18 个在办项目”。
3. 页面固定显示当前企业、项目类型、指定项目和配置版本，防止发布错范围。
4. 恢复继承、批量迁移、停用字段和回滚均先展示影响范围并二次确认。
5. 普通文案、说明和排序调整可采用低风险快速发布；权限、金额、准入、公式和工作流变更进入高风险审批。

### 24.4 配置健康度

管理驾驶舱持续展示未使用字段、失效字典、无负责人任务、长期停留实例、规则冲突、失败集成、待迁移实例和即将到期密钥。健康度只反映已验证的配置与运行事实，不使用无法解释的综合评分替代具体问题。

## 25. 通知与统一任务协议

通知渠道至少抽象为站内消息、邮件、短信和企业协同工具，具体启用渠道由集成配置决定。任务是需要处理的业务对象，通知只是提醒任务或事实发生的消息，二者不得混用。

每条通知保存业务键、接收人、渠道、模板版本、发送状态和关联任务。相同事件和接收人的重复通知按业务键去重。系统支持工作时间、静默时段、首次提醒、重复提醒、超时升级、负责人缺失时的上级或管理员兜底。

任务完成、取消、转交或阶段回退后，后续提醒必须同步停止。已发送消息不删除，必要时发送更正通知。通知模板可以配置文案，但不得泄露接收人无权查看的金额、附件或项目字段。

## 26. API、集成与异步任务规范

### 26.1 通用 API 约定

1. 写接口支持 `Idempotency-Key`，同一键和相同请求返回相同结果；同一键不同请求返回冲突。
2. 可并发修改的资源带 `version` 或 ETag，更新时必须提供预期版本。
3. 错误响应包含稳定业务错误码、用户可理解说明、关联字段和跟踪 ID，不返回堆栈或密钥。
4. 列表接口统一分页、排序、筛选和数据范围；导出接口复用同一筛选和权限决策。
5. API 路径和请求结构版本化，废弃版本设置迁移期，不允许静默改变已有字段语义。

### 26.2 异步任务

文件识别、批量迁移、导出、通知和配置影响分析通过异步任务执行。创建任务后返回任务 ID，客户端通过查询或受控推送获取进度。任务状态统一为等待、运行、成功、部分成功、失败、已取消，并保存处理数量、失败明细和重试入口。

### 26.3 外部集成

外部回调必须校验签名、时间戳和重放窗口。集成适配器保存供应商请求 ID、内部业务键、脱敏请求摘要、响应状态和耗时。任何供应商字段必须在适配器层转换为内部模型，不得直接进入核心业务表。

## 27. 非功能指标与工程测试门槛

### 27.1 首期服务指标

以下为首期工程基线，正式上线前根据真实数据量压测后确认：

| 指标 | 基线要求 |
| --- | --- |
| 常用页面和已发布表单元数据 | 内网正常条件下 P95 小于 2 秒 |
| 普通表单保存和阶段准入校验 | P95 小于 1.5 秒，不含外部 AI 任务 |
| 阶段推进 | 返回明确成功或失败，不允许长时间无状态；外部动作异步执行 |
| 可用性 | 月度核心业务可用性目标不低于 99.5% |
| 备份 | 数据库每日全量并配合增量或日志备份，附件按存储策略冗余 |
| 灾难恢复 | 初始目标 RPO 不高于 24 小时、RTO 不高于 4 小时，投产前完成恢复演练 |
| 审计日志 | 高风险业务和配置操作完整记录，禁止普通管理员修改 |

文件最大大小、最大页数、并发识别量和单租户配额由系统设置维护，同时受服务器和供应商硬限制约束。前端必须在选择文件前展示允许类型和当前限制，失败时说明具体原因。

### 27.2 可观测性

服务统一记录跟踪 ID、结构化日志、接口耗时、任务队列长度、失败率和外部供应商健康状态。日志不得记录密码、令牌、完整身份证件、未脱敏合同正文或文件内容。错误告警必须关联具体服务、任务和项目，但遵循接收人的数据权限。

### 27.3 自动化测试

1. 生命周期准入和异常回路使用状态转换测试，覆盖禁止跳阶段和整改复验。
2. 规则引擎使用单元测试和属性测试，验证空值、边界金额、日期和冲突规则。
3. 工作流使用图结构校验、并行汇合、幂等、重试、补偿和事件重放测试。
4. 权限使用角色、项目范围、字段和资料动作矩阵测试，覆盖列表、详情、导出和下载。
5. 模板发布和迁移使用历史版本回归、失败回滚和数据对账测试。
6. AI 使用固定金标准集执行字段级回归，禁止只用开发样本验收。
7. 文件服务测试原件哈希、版本、权限、恶意文件拦截和派生文件关系。
8. 上线前执行数据库恢复、队列积压、供应商不可用和通知失败演练。

### 27.4 发布门禁

存在核心流程测试失败、权限越权、迁移对账不一致、审计日志缺失、AI 高风险字段回归下降或无法恢复备份时，版本不得发布。生产发布保存代码版本、数据库迁移版本、配置发布包和回滚说明。
