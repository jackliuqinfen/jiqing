# 合同建档应急降级与手动辅助设计

日期：2026-07-15  
状态：已实施，待生产走查
适用范围：项目管理中的“上传合同创建项目”流程

## 1. 目标与边界

合同建档必须同时具备 AI 主通道和人工应急通道。AI 不可用、文件无法解析或网络异常时，用户不能丢失已录入信息，也不能被迫等待管理员处理。

本方案坚持以下业务边界：

1. 没有成功保存合同文件时，只能保存“项目建档草稿”，不得写入正式项目主档案。
2. 合同文件已成功保存但 OCR 失败时，可进入空白人工复核，逐项确认关键合同字段后正式建档。
3. AI 只提供建议；人工确认值不得被后续识别结果自动覆盖。
4. 正式建档仍复用现有合同复核确认链路，不新增绕过生命周期门禁的项目创建接口。
5. 不生成模拟识别结果，不用默认值伪装 AI 已成功识别。

## 2. 用户入口与界面流程

### 2.1 弹窗起始页

弹窗首次打开时显示三个并列模式卡片：

- **系统 AI 识别（推荐）**：选择合同，上传后由系统自动识别，再进入人工复核。
- **导入外部 AI 结果**：先上传并保存合同，再复制系统提供的固定提示词，将合同交给豆包、ChatGPT 等外部 AI；把其返回的 Markdown 结果粘贴回系统，经白名单校验后进入人工复核。该路径不依赖系统 OCR API。
- **完全手动填写**：人工录入合同关键字段；合同上传成功后可正式复核，未上传成功时只能保存草稿。

外部 AI 通道必须在界面中明确提示：合同可能包含敏感商业信息，用户应遵循本单位的数据安全要求，不得把不允许外发的合同上传至第三方服务。

起始页同时展示当前用户未完成的建档草稿，支持继续填写和放弃。不得展示其他用户的未绑定草稿，管理员除外。

### 2.2 AI 通道降级

| 故障点 | 系统动作 | 用户可选操作 |
| --- | --- | --- |
| 文件格式或大小不合规 | 不创建文档记录，保留本地已选文件 | 重新选文件、转手动草稿 |
| 网络或服务器上传失败 | 不宣称文件已保存，保留已填字段 | 重试上传、保存手动草稿 |
| 文件已保存但页面解析失败 | 保留文档及版本记录 | 重新解析、进入手动复核 |
| OCR 未配置或不可用 | 保留文档及版本记录 | 重新识别、进入手动复核 |
| OCR 返回异常或质量不足 | 保留文档及错误原因 | 重新识别、进入手动复核、重新扫描 |

所有错误提示必须使用真实错误原因，不得统一显示为“AI 服务未就绪”。

### 2.3 手动辅助建档

手动模式使用现有合同字段语义和校验规则，按“项目信息、参建单位、合同信息”分组。关键字段逐项确认，不提供一键批量确认。

手动字段的数据来源标记为：

- `manual_entry`：用户主动手工录入；
- `ai_suggestion`：AI 建议、尚未确认；
- `human_confirmed`：人工已确认，可写入正式业务事实。

用户进入手动模式时必须填写简短原因，选项为“AI 未就绪、识别失败、扫描质量不足、上传暂时失败、主动手动录入”，并可补充说明。

### 2.4 导入外部 AI 结果

系统提供“复制提示词”按钮。提示词要求外部 AI 仅输出一段 Markdown，并在其中包含唯一的 `json` 代码块。JSON 固定采用以下结构：

```json
{
  "schemaVersion": "contract.v1",
  "fields": {
    "project.name": {
      "value": "项目名称",
      "evidence": "合同中的对应原文",
      "page": 1
    }
  }
}
```

系统不解析自由文本，只提取唯一的 `json` 代码块，并执行以下校验：

1. 文本总长度和 JSON 字段数量不得超过后端限制；
2. `schemaVersion` 必须等于 `contract.v1`；
3. `fields` 中的语义键必须属于合同字段白名单；
4. 值类型必须符合字段定义，未知键、重复代码块或非法 JSON 一律拒绝；
5. 外部 AI 返回的置信度、坐标和供应商结论一律不作为可信证据；
6. `evidence` 和 `page` 仅作为人工核对提示，不生成伪造版面坐标；
7. 导入值统一标记为 `ai_suggestion`，关键字段仍需逐项人工确认。

外部 AI 结果只有在合同文件已经保存到本系统后才能进入正式复核。未保存合同文件时，外部导入按钮不可提交；用户可切换到手工模式保存建档草稿，但不得创建正式项目。

## 3. 两类手动结果

### 3.1 无合同文件：建档草稿

上传未成功或用户暂时没有可上传文件时，系统保存独立的建档草稿：

- 不创建 `projects`、合同事实或生命周期事件；
- 不生成项目编号；
- 状态显示为未关联合同原件，并出现在当前用户的未完成草稿列表；
- 后续补传合同成功后进入合同复核流程；
- 草稿中的人工值用于复核页预填，但仍需逐项确认。

草稿状态：`draft`、`document_attached`、`completed`、`abandoned`。

### 3.2 已有合同文件：人工复核

文件已保存而 OCR 失败时，用户点击“进入手动复核”，后端创建独立的 `manual-entry` 识别任务：

- 关联同一个不可变合同版本；
- 不伪造 OCR 文本块、坐标或置信度；
- 按 `contract.v1` 物化空白字段；
- 任务直接进入 `review_ready`，打开现有复核工作台；
- 字段显示“人工录入”，无原文定位框时允许人工填写；
- 关键字段仍必须逐项确认，现有金额、日期和合同门禁校验继续生效；
- 确认后仍由现有合同确认服务原子化创建项目、合同快照和生命周期事件。

原 OCR 任务和错误记录保持不变，手动任务通过来源任务 ID 与操作日志关联，确保审计可追溯。

## 4. 数据模型

### 4.1 `project_intake_drafts`

新增建档草稿表，核心字段：

| 字段 | 说明 |
| --- | --- |
| `id` | 草稿 ID |
| `owner_user_id` | 草稿所有人 |
| `status` | 草稿状态 |
| `document_id` / `document_version_id` | 补传成功后关联，不成功时为空 |
| `schema_version` | 固定为 `contract.v1` |
| `values_json` | 按合同语义键保存的人工输入 |
| `fallback_reason` / `fallback_note` | 降级原因与说明 |
| `created_at` / `updated_at` | 时间戳 |
| `completed_project_id` | 正式建档后回写 |

`values_json` 只保存表单事实，不保存文件内容、密钥或供应商原始响应。

### 4.2 `recognition_jobs`

新增可空字段 `source_recognition_job_id`，用于记录手动复核任务来源；新增 `fallback_reason`、`fallback_note`，用于持久化降级原因。约束如下：

- 手动任务 `adapter_key = manual-entry`，外部导入任务 `adapter_key = external-ai-paste`；
- 允许对已保存合同主动选择备用方式，也允许从 `failed` 或 `manual_required` 的系统任务降级；
- 来源任务和手动任务必须关联同一 `document_version_id`；
- 同一来源任务使用幂等键，重复点击只返回同一手动任务。

## 5. 接口设计

### 5.1 草稿接口

- `POST /api/project-intake-drafts`：新建草稿。
- `GET /api/project-intake-drafts`：获取当前用户草稿，管理员按现有权限可查看全部。
- `GET /api/project-intake-drafts/{id}`：读取草稿。
- `POST /api/project-intake-drafts/{id}`：保存字段、原因、关联文档或正式建档后的项目 ID。
- `POST /api/project-intake-drafts/{id}/abandon`：放弃草稿。

所有写接口仅允许当前系统中的管理员或编辑者；查看者不可写。普通用户只能访问自己的草稿，管理员可按权限查看全部。

### 5.2 人工复核接口

已存在失败任务时使用：`POST /api/document-recognition-jobs/{jobId}/manual-review`。

用户主动选择手工复核时使用：`POST /api/document-versions/{versionId}/manual-review`。

请求：

```json
{
  "idempotencyKey": "manual-review:<job-id>:<stable-client-key>",
  "fallbackReason": "ocr_failed",
  "fallbackNote": "可选说明",
  "draftId": "可选草稿ID"
}
```

响应返回新的人工任务及 `reviewId`。接口必须校验任务状态、文档版本归属、用户权限和草稿所有权。

### 5.3 外部 AI 结果导入接口

已存在失败任务时使用：`POST /api/document-recognition-jobs/{jobId}/external-import`。

用户主动选择外部 AI 时使用：`POST /api/document-versions/{versionId}/external-import`。

请求：

```json
{
  "idempotencyKey": "external-import:<job-id>:<stable-client-key>",
  "markdown": "外部 AI 返回的完整 Markdown",
  "draftId": "可选草稿ID"
}
```

后端解析并校验唯一 JSON 代码块，按 `contract.v1` 物化白名单字段和缺失字段，创建 `external-ai-paste` 复核任务并返回 `reviewId`。接口不得接收客户端直接指定适配器、文档版本、项目 ID 或字段定义。

## 6. 后续 AI 识别与差异处理

人工确认后再次获得 AI 结果时：

1. 不覆盖 `human_confirmed` 值；
2. 对相同语义键生成差异提示；
3. 用户可选择保持人工值或采用新建议；
4. 修改关键金额、主体或日期仍需填写原因并产生操作日志；
5. 已创建正式项目时，不通过 OCR 结果直接修改项目主档案。

第一期只实现差异提示的数据边界和“不覆盖”规则，不新增自动合并策略。

## 7. 错误文案

- 上传大小超限：`文件超过系统允许的最大上传大小（{n} MB），请压缩后重试或先保存手动草稿。`
- 格式不支持：`当前格式暂不支持，请转换为 PDF、图片或先保存手动草稿。`
- 上传失败：`合同尚未保存到服务器。你可以重试上传，或先保存手动草稿，稍后补传合同。`
- OCR 未配置：`合同已安全保存，但 AI 识别服务尚未配置。可以进入手动复核，不影响继续建档。`
- 解析失败：`合同已安全保存，但当前文件无法完成自动解析。可以重新扫描、重新识别或进入手动复核。`

提示必须明确文件是否已经成功保存，避免用户误以为资料已归档。

## 8. 审计、权限与安全

后端必须记录以下持久化操作：降级原因、草稿创建与修改、合同关联、进入手动复核、字段确认、正式建档和草稿完成或放弃。

日志展示姓名并保留账号 ID。文件访问、草稿访问、人工复核和正式确认均执行后端权限校验，不能只靠前端隐藏按钮。

## 9. 验收标准

1. 弹窗起始页可主动选择系统 AI、导入外部 AI 结果或完全手动填写。
2. 上传失败后，已填信息不丢失，可保存草稿，但数据库中不产生正式项目。
3. 文件已保存但 OCR 失败时，可进入空白复核工作台并手工填写。
4. 人工任务不包含伪造 OCR 坐标、文本或置信度。
5. 关键合同字段未逐项确认时不能正式建档。
6. 手动复核确认后，项目、合同快照和生命周期事件按现有原子事务创建。
7. 重复点击手动复核不会创建重复任务或重复项目。
8. 后续 AI 建议不会覆盖人工确认值。
9. 查看者不能创建草稿、启动手动复核或确认项目。
10. 所有降级动作在操作日志中可追溯。
11. 外部 AI Markdown 中存在未知字段、多个 JSON 代码块或非法结构时，后端拒绝导入并返回准确错误。
12. 外部导入值只作为建议，未逐项人工确认时不能正式建档。
13. 已保存草稿可由原所有人继续填写或放弃，正式建档后自动标为完成。
14. 上传失败时仍能保存无文件草稿，提示必须明确文件尚未上传成功。

## 10. 测试范围

- 数据迁移：草稿表、来源任务外键、幂等约束和回滚。
- 后端契约：鉴权、归属、状态门禁、重复请求、草稿到正式项目的转换。
- 领域测试：无文件只能草稿、人工字段不要求伪造锚点、关键字段逐项确认。
- 前端流程：三入口、提示词复制、外部结果粘贴与校验、错误降级、草稿恢复、手动复核、准确错误文案。
- 回归测试：AI 正常识别路径、OCR 重试、合同确认和正式项目创建不受影响。
- 生产验收：真实扫描合同分别验证 AI 成功、OCR 失败转人工、上传失败存草稿三条路径。

## 11. 实施顺序

1. 数据迁移与草稿仓储。
2. 手动复核与外部 AI 导入任务服务和接口。
3. 草稿接口及权限。
4. 弹窗三入口、提示词复制、结果导入、降级动作和草稿恢复。
5. 操作日志与待办。
6. 自动化测试、生产构建和真实合同走查。
