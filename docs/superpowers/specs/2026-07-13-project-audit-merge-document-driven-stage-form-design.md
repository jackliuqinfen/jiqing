# 项目审计一体化与文件驱动阶段表单第一期设计

- 状态：已确认
- 确认日期：2026-07-13
- 文档版本：1.0
- 适用范围：项目管理、审计视图、资料中心、后台管理、AI 文档识别
- 关联总设计：`2026-07-10-lifecycle-configurable-form-engine-design.md`

## 1. 背景

工程项目的数据不是在项目创建时一次性产生，而是随合同签订、进场施工、竣工验收、送审、一审、二审、最终定案和归档逐步形成。系统不得在合同阶段要求用户提供验收证明、审计单位或审定金额，也不得让用户脱离业务凭证直接填写高风险事实。

本设计将项目管理与审计合并为一个项目生命周期工作区，并以正式业务文件驱动阶段表单。第一期优先解决三个关键断点：

1. 上传施工合同后创建正式项目，避免重复录入项目、主体、金额和付款条款；
2. 上传竣工验收证明后确认验收事实，验收合格后才开放送审；
3. 上传最终审定单后确认审定事实，区分工程审定金额、费用扣减和最终结算金额。

## 2. 已确认决策

1. 审计不再作为独立项目数据域，而是项目管理左侧二级导航中的“审计视图”。
2. 招投标中的中标记录在合同签订前保持为“已中标待签约”，不创建正式项目主档案。
3. 项目管理中的“新增项目”改为合同先行：上传合同、AI 识别、人工确认后才创建正式项目。
4. 所有正式生命周期凭证均按扫描件处理。PDF 自带文本层只能作为辅助证据，不能跳过逐页图像解析。
5. 阶段表单由文件驱动：先上传当前阶段凭证，再由 AI 预填当前阶段表单，关键字段经人工确认后形成阶段事实。
6. 第一批正式识别类型为施工合同、竣工验收证明和最终审定单。
7. 合同金额、付款条款、验收结论、审定金额和生命周期阶段不得由 AI 自动确认或自动推进。
8. 后台可配置阶段表单、字段映射、资料规则和置信度阈值，但不能取消核心顺序和人工确认门槛。

## 3. 范围与非目标

### 3.1 第一期范围

- 项目管理内提供项目台账、生命周期视图和审计视图；
- 合同上传、扫描件处理、结构化提取、证据定位、人工复核和正式项目创建；
- 竣工验收证明上传、结构化提取、项目匹配、人工复核和验收阶段确认；
- 最终审定单上传、复杂表格提取、金额口径拆分、项目匹配、人工复核和定案事实写入；
- 文件识别任务、失败重试、版本、哈希、证据锚点、操作日志；
- 后台配置三类文档模板、字段映射、校验规则、复核角色和发布版本；
- 旧审计入口的兼容跳转和历史数据只读兼容。

### 3.2 第一期非目标

- 不让 AI 自动推进项目阶段；
- 不让 AI 自动批准金额、付款条款或验收结论；
- 不一次性识别全部工程资料类型；
- 不建设自由脚本式 BPM；
- 不把 OCR 结果直接写入正式业务表；
- 不使用模拟项目、模拟金额或虚构识别结果填充生产页面；
- 不在 Obsidian 或设计文档中保存原始业务文件、银行信息、联系电话等敏感内容。

## 4. 信息架构

顶部平台导航保留“项目管理”，取消独立“审计”产品入口。项目管理左侧二级导航建议为：

```text
项目管理
├─ 项目台账
├─ 生命周期
├─ 审计视图
├─ 待办与异常
└─ 项目资料
```

“审计视图”是同一项目集合的阶段视图，不复制项目名称、编号、建设单位、施工单位、负责人、合同和资料。审计专属字段作为项目下的审计批次、审计阶段事件和审定记录存在。

历史 `/audit` 路由进入兼容层，跳转到项目管理的审计视图，并保留原筛选条件和项目定位参数。完成迁移前不得同时维护两套可写项目事实。

## 5. 正式项目创建：合同先行

### 5.1 招投标移交边界

中标确认只创建“已中标待签约”移交记录、合同签订待办和中标资料目录，不创建正式项目主档案。中标记录可以被放弃、取消或长期待签约，历史仍需保留。

### 5.2 新建项目流程

```text
上传施工合同
→ 文件安全与重复检查
→ 全页扫描件解析
→ 文档分类与合同字段提取
→ 项目、主体、金额和条款交叉校验
→ 人工逐字段复核
→ 确认合同事实
→ 创建正式项目主档案、合同记录和阶段快照
→ 生成付款条款草稿、施工阶段资料目录和待办
```

没有合同的历史项目只能由管理员通过“历史项目初始化”进入，必须填写初始化原因、事实日期、缺失资料和责任人，并保留完整日志。该入口不能伪装成普通新增项目。

### 5.3 合同阶段目标字段

| 字段组 | 目标字段 | 处理规则 |
| --- | --- | --- |
| 项目 | 项目名称、项目地点、工程内容、合同类型 | AI 建议，人工确认 |
| 主体 | 建设单位、施工单位 | 先匹配主数据字典；新主体需人工确认后沉淀 |
| 人员 | 项目经理、合同联系人 | 人员匹配失败时创建候选，不静默新建正式账号 |
| 合同 | 合同名称、编号、签订日期、签订地点、工期 | 日期和工期执行一致性校验 |
| 金额 | 合同小写金额、中文大写金额、暂列金、暂估价 | 大小写不一致时阻断确认 |
| 条款 | 付款节点、累计比例、付款基数、发票条件、质保金 | 条款保留原文证据和拆分过程 |

## 6. 扫描件优先处理流水线

所有正式凭证采用同一基础流水线：

```text
原件上传
→ 文件哈希、病毒和重复检查
→ 每页按 300 DPI 渲染为图像
→ 自动旋转、纠偏、去噪、阴影和透视修正
→ 版面 OCR、表格、手写、印章和签名区域检测
→ 页级分类与文档级分类
→ 按文档模板执行 JSON Schema 字段提取
→ 项目、主体、日期、金额和阶段规则校验
→ 左图右表人工复核
→ 写入阶段表单草稿
→ 人工确认后生成正式阶段事件
```

PDF 文本层只用于补充候选文字、搜索和比对。系统始终保存页面图像坐标作为证据锚点，避免错误文本层、乱码或缺字被当作真实内容。

## 7. 文件驱动阶段表单

### 7.1 核心规则

1. 当前阶段只显示当前能够产生的文件、问题和字段；
2. 未达到阶段时，未来字段隐藏且不计资料缺失；
3. 进入正式节点前先上传对应凭证；
4. AI 只生成表单草稿，不生成业务事实；
5. 人工确认后形成不可变阶段事件和表单快照；
6. 更换文件版本或更正字段时生成新版本，不覆盖旧证据；
7. 凭证与项目不匹配时阻断写入，并允许改选项目或转入待认领队列。

### 7.2 阶段与文件映射

| 生命周期节点 | 主凭证 | 预填表单 | 确认结果 | 核心阻断 |
| --- | --- | --- | --- | --- |
| 已签订合同 | 施工合同 | 项目及合同确认表 | 创建正式项目并进入合同阶段 | 主体或金额未确认 |
| 验收合格 | 竣工验收证明 | 竣工验收确认表 | 记录验收事实并开放送审准备 | 未竣工、结论非合格或项目不匹配 |
| 一审完成 | 一审报告或审定单 | 一审结果确认表 | 形成一审批次和金额事实 | 报告缺失或金额未确认 |
| 二审完成 | 二审报告或审定单 | 二审结果确认表 | 形成二审批次和金额事实 | 一审前置事实不完整 |
| 最终定案 | 最终审定单 | 最终定案确认表 | 更新结算基数并生成后续待办 | 项目不匹配或最终金额口径不明 |

第一期实现已签订合同、验收合格和最终定案三类；一审、二审沿用同一协议，在后续发布中增加模板，不另造处理链路。

### 7.3 竣工验收确认表

目标字段包括项目名称、施工单位、监理单位、设计单位、建筑面积、合同价、开工日期、竣工日期、验收日期、验收结论和参与单位签章情况。

系统必须同时校验：

- 当前项目已进入竣工待验收阶段；
- 文件中的项目名称、施工单位与项目主档案匹配；
- 验收日期不早于竣工日期；
- 验收结论为合格时才允许开放送审；
- 表格内容异常，例如单位字段填入项目名称，必须标记人工核验，不能覆盖合同主体。

### 7.4 最终定案确认表

目标字段包括项目名称、项目编号、建设单位、施工单位、审核类型、合同价、送审金额、一审审定金额、二审审定金额、审核费用扣减、最终结算金额、核减额、核减率、定案日期和中文大写金额。

“工程审定金额”和“扣除审核费用后的最终结算金额”必须分字段存储。表格中汇总金额、费用扣减和大写金额不一致时，系统阻断确认并展示计算过程。

## 8. 三份真实样例形成的设计约束

样例只用于字段和规则验证，原件保留在本地临时验证目录，不进入代码仓库、公开测试集或 Obsidian。

### 8.1 施工合同样例

样例为 30 页完整扫描件，无可用文本层，包含项目主体、合同金额、固定单价合同、工期、项目经理、签订日期和多段付款条款。付款条款分散在合同中部页面，且同时存在履约保证金与质保金，识别模型必须按条款语义和证据页拆分，不能仅靠关键词合并。

### 8.2 竣工验收证明样例

样例为单页扫描表格，混合打印文字、手写日期、签章和多个参与单位。系统需支持合并单元格、手写候选、印章遮挡和表格字段错填检测。验收证明中的约数合同价不得静默覆盖合同精确金额。

### 8.3 最终审定单样例

样例属于另一项目，不能与前两份文件自动关联。该文件同时包含送审、一审、二审、审核费用扣减和扣费后最终金额，证明项目匹配与金额口径拆分是正式写入前的强门槛。疑似缺失小数点的比率字段必须进入人工复核。

## 9. 人工复核体验

复核工作台采用大弹窗或全屏工作区：

- 左侧为原始页面，支持缩放、翻页、旋转和证据区域高亮；
- 右侧按业务分组展示候选字段、建议值、原文、页码、置信度和校验结果；
- 点击字段时左侧自动定位到证据区域；
- 每个字段支持接受、修改、拒绝和标记无法识别；
- 低置信度、跨文件冲突和关键金额默认展开；
- 顶部展示文档类型、匹配项目、处理版本和整体阻断项；
- 底部仅在阻断项清零后允许“确认并生成阶段事实”。

人工修改必须保留 AI 候选值、修改后值、修改人、时间和原因。批量接受不适用于合同主体、合同金额、付款条款、验收结论和审定金额。

## 10. 数据模型

| 实体 | 关键职责 |
| --- | --- |
| `Document` | 原始业务文件、文件类型、所属项目候选、哈希、安全状态 |
| `DocumentVersion` | 原件版本、上传人、上传时间、来源和替代关系 |
| `DocumentPage` | 页面序号、渲染图、宽高、旋转和预处理版本 |
| `OcrBlock` | 页面文字块、表格单元格、手写或印章区域及坐标 |
| `ExtractedField` | 字段键、候选值、规范化值、置信度和模型版本 |
| `EvidenceAnchor` | 文件版本、页码、边界框、原文片段和图像片段引用 |
| `ReviewDecision` | 接受、修改、拒绝、复核人、原因和时间 |
| `StageFormSnapshot` | 阶段表单发布版本、确认值和生成时点的不可变快照 |
| `StageEvent` | 合同确认、验收通过、审定确认等正式生命周期事实 |

正式业务字段只引用已确认的 `ReviewDecision`。删除或替换文档不得破坏历史 `StageFormSnapshot` 和 `StageEvent` 的证据链。

## 11. 项目匹配与冲突规则

匹配按项目编号、项目名称、建设单位、施工单位、合同编号和金额分层评分，但高分只代表推荐，不代表自动确认。

以下情况必须阻断自动关联：

1. 文件项目编号与当前项目明确不一致；
2. 项目名称差异超过配置阈值且无合同编号支持；
3. 建设单位和施工单位均不匹配；
4. 合同、验收或审定金额存在无法解释的数量级差异；
5. 当前生命周期不允许该文档形成的阶段事实；
6. 同一文件哈希已在其他项目形成正式记录。

无法匹配的文件进入“待认领资料”，由有权限用户选择项目并说明理由。跨项目移动已确认文件属于高风险更正，必须重新复核并保留原关联历史。

## 12. 后台管理能力

管理员可配置：

- 文档类型与适用生命周期节点；
- 页面分类、目标 JSON Schema 和字段字典；
- 字段到核心数据或扩展字段的映射；
- 每个字段的证据要求、置信度阈值和复核角色；
- 项目匹配、金额、日期、主体和阶段校验规则；
- 阶段表单布局、可见性、必填、锁定和更正规则；
- 失败重试、供应商降级、成本配额和人工兜底；
- 草稿、模拟、发布、版本、影响分析和回滚。

系统保护合同创建项目、验收合格后送审、审定金额人工确认等核心规则，管理员不能通过配置关闭。

## 13. API 与异步任务边界

建议内部协议按职责拆分：

```text
POST /api/documents/uploads
POST /api/document-recognition-jobs
GET  /api/document-recognition-jobs/{jobId}
GET  /api/document-reviews/{reviewId}
POST /api/document-reviews/{reviewId}/decisions
POST /api/document-reviews/{reviewId}/confirm
POST /api/projects/from-confirmed-contract
POST /api/projects/{projectId}/stage-evidence
POST /api/projects/{projectId}/stage-events
```

上传、识别和确认分别授权。识别任务使用幂等键、版本和状态机；网络重试不得重复创建文档、项目或阶段事件。外部 OCR 与大模型通过适配器接入，供应商响应不得直接写入核心表。

## 14. 安全、版本与降级

1. 原件和页面派生文件使用独立对象存储权限，下载和预览受项目数据范围控制；
2. 文件内容、OCR 原文和模型请求不写入普通应用日志；
3. 第三方服务只接收批准出域的最小必要内容；
4. 模型、提示词、字段 Schema、后处理规则和供应商版本全部记录；
5. 识别失败可重试、切换已批准供应商或转人工录入；
6. 服务不可用时不阻塞原件上传，任务进入等待或人工处理队列；
7. 正式确认前允许替换文件；确认后上传新版本进入更正流程；
8. 临时页面图和识别缓存按后台保留策略清理，正式证据链按项目归档策略保留。

## 15. 第一期实施拆分

### 15.1 基础底座

- 文件原件、版本、页面、哈希和异步任务；
- 300 DPI 页面渲染与预处理；
- OCR、版面、表格和结构化提取适配器；
- 证据锚点、人工复核、字段决定和操作日志；
- 项目匹配与跨文件校验服务。

### 15.2 合同创建项目

- 合同上传入口替换空白新增项目入口；
- 合同字段和付款条款提取；
- 主体、人员和金额复核；
- 确认后原子创建项目、合同、表单快照和阶段事件。

### 15.3 验收与定案

- 验收证明识别、手写和表格复核；
- 验收合格门槛及送审开放；
- 最终审定单识别、项目阻断和金额口径拆分；
- 定案确认后更新结算基数并生成后续待办。

### 15.4 项目审计一体化

- 项目管理左侧增加审计视图；
- 审计看板读取同一项目和阶段事件；
- 旧 `/audit` 路由兼容跳转；
- 停止新增重复审计项目主数据。

## 16. 第一期验收标准

1. 未上传并确认合同，普通用户不能创建正式项目；
2. 中标记录只生成待签约移交，不自动生成正式项目；
3. 三类文档均逐页渲染后识别，不因 PDF 有文本层而跳过扫描件流程；
4. 每个候选字段都能定位到文件版本、页码和区域；
5. 合同主体、金额、日期和付款条款必须人工确认后才能创建项目；
6. 创建项目接口具备幂等性，同一确认任务不能生成两个项目；
7. 验收证明项目不匹配、结论未确认或非合格时不能开放送审；
8. 当前项目未验收合格时，送审、一审、二审和定案表单不可见且接口拒绝推进；
9. 最终审定单属于其他项目时必须阻断关联并给出明确冲突项；
10. 工程审定金额、费用扣减和最终结算金额分开保存并展示计算关系；
11. AI 候选、人工修改、正式值、模型版本和证据链可完整追溯；
12. 新文件版本和字段更正不覆盖历史快照；
13. OCR 服务不可用时可等待、重试或转人工，不丢失原件；
14. 审计视图与项目台账展示同一项目基础数据，不发生重复录入；
15. 生产页面不出现模拟项目、模拟金额或无法追溯的识别结果。

## 17. 外部能力要求

第一期落地需要可替换的 OCR 与结构化提取能力，至少满足：

- 中文印刷体与手写日期识别；
- 多页扫描 PDF、自动纠偏和低清图像增强；
- 复杂表格、合并单元格和跨行表头解析；
- 印章、签名和遮挡区域检测；
- 文字块、表格单元格和候选字段坐标返回；
- 按 JSON Schema 输出结构化候选值和证据引用；
- 企业确认的数据出域、保留、删除和服务区域要求。

供应商和部署方式在实施启动前根据数据合规、样本准确率、成本和可用性评估确定。无论采用云 API 还是本地服务，业务层只依赖内部适配器协议。

## 18. 主要风险与控制

| 风险 | 控制措施 |
| --- | --- |
| 扫描质量差导致错识 | 图像质量评分、自动增强、低质量阻断和人工录入 |
| 印章或手写遮挡关键字段 | 区域检测、多引擎候选和逐字段复核 |
| 同名项目错误关联 | 多字段匹配、强冲突规则和人工确认 |
| 金额口径混淆 | 金额类型化、公式校验、大写比对和计算过程展示 |
| AI 版本升级造成回归 | 独立金标准、版本发布和回滚 |
| 外部服务不可用 | 异步队列、重试、批准的供应商降级和人工兜底 |
| 一次范围过大 | 第一期只闭环合同、验收证明和最终审定单 |
